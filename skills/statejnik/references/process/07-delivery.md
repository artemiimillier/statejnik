# 07. Доставка и уведомление

**Цель:** опубликовать именно принятую версию один раз и подтвердить, что она на месте. Навигация - [INDEX](INDEX.md).

**Роли:** автор выполняет доставку; **сверяющий финал** - тот же свежий субагент, что закрывал [final-humanization](final-humanization.md), или ещё один свежий субагент через `delegate_task` для сверки живой страницы.

**Вход:**
- `work/<slug>/final.md` - точный файл, прошедший [06-review](06-review.md) и [final-humanization](final-humanization.md); `work/<slug>/review.md` с accept;
- `statejnik.yaml`: `publish.auto`, `publish.default`, `publish.targets`, `project.domain`, `project.content_path`;
- [publishers](../publishers.md) - настройка площадок, [owner-report](../owner-report.md) - формат уведомления.

**Выход:** запись в `work/published.json` (slug, id, url на каждой площадке), `work/<slug>/delivery.md` (что отправлено, куда, со статусом; результат сверки живой страницы), одно уведомление владельцу. Либо точный статус: `blocked` / `draft` / `published-with-issue` с причиной.

## Шаги

1. **Всё содержательное - до приёмки.** Автоссылки, нормализация, правка ссылок делаются до финальной вычитки. Если что-то изменило `final.md` хотя бы на байт после приёмки - вернуться в [06-review](06-review.md), шаг 10. Доставка не пишет текст заново.
   *Готово:* `final.md` совпадает с принятой версией (diff пустой).

2. **Площадка готова.**
   ```
   python3 $SKILL_DIR/scripts/publish.py check <площадка>
   ```
   Ошибку доступа (401/403) не лечить чужими ключами - сообщить владельцу. Другие ошибки сначала диагностировать; публичные тестовые записи на сайте не создавать.
   *Готово:* check проходит.

3. **Отправка черновиком (по умолчанию).**
   ```
   python3 $SKILL_DIR/scripts/publish.py send <площадка> work/<slug>/final.md --status draft
   ```
   Боевая публикация `--status publish` - **только** если `publish.auto: true` или владелец явно сказал «публикуй». Статья с `status: blocked` или `rejected` в служебных полях не публикуется (скрипт остановит - не обходить). Для площадок, где id вписывается вручную, - `publish.py record <площадка> <slug> <id> [url]`.
   *Готово:* в `work/published.json` есть запись slug → id/url для каждой площадки.

4. **Неопределённый ответ.** Таймаут, обрыв, непонятный код - сначала проверить фактическое состояние на площадке (открыть админку, ленту или URL), и только потом решать, повторять ли. Не отправлять повторно вслепую: повтор не должен дать второй записи. «Уже опубликовано» - сверить, не делать дубль. Временный сбой - ограниченное число повторов с паузой; 429 - ожидание.

5. **Сверка с тем, что на площадке.** Если площадка изменила текст (нормализация разметки, обрезка, экранирование) - это не та версия, которую принимали. Согласовать локальный `final.md`, пройти затронутые проверки и финальную вычитку заново, отправить снова. Старую приёмку за новую версию не выдавать.

6. **Проверка живой страницы** (после боевой публикации; для черновика - предпросмотр, если площадка даёт). Открыть живой URL (`web_extract` или браузер) и сверить:
   - страница открывается, код 200, правильный H1;
   - **текст целиком на месте**: все H2, абзацы, списки, таблицы и блоки кода из `final.md`, ничего не обрезано, код не сломан, нет мусора вроде `[object Object]`, неотрендеренной разметки, служебных маркеров;
   - CTA на месте и ведёт на `cta.url`; внутренние ссылки ведут на существующие страницы;
   - canonical, отсутствие noindex, наличие в sitemap, текст доступен роботам без выполнения скриптов; структурированные данные соответствуют содержимому;
   - правовую и публичную безопасность повторить на фактически отрендеренной странице (это повтор, а не первая проверка).
   Проверку десктопа, мобильной версии и превью для соцсетей делать, если есть инструмент; нет инструмента - честно записать «не проверено», HTML не доказывает визуальную корректность.
   *Готово:* в `work/<slug>/delivery.md` - по каждому пункту pass или конкретный дефект.

7. **Индексация.**
   ```
   python3 $SKILL_DIR/scripts/publish.py ping <url>
   ```
   IndexNow только уведомляет Яндекс и Bing, не гарантирует индексацию. Для Google - карта сайта в Search Console.

8. **Закрытие темы.** Отметить тему в `work/plan.md` как сделанную **только** после подтверждённой публикации. Строку плана закрывать, лишь если тема реально использована. Записать итог в бортовой журнал `work/journal.md` ([08-feedback](08-feedback.md)).

9. **Одно уведомление владельцу** - по [owner-report](../owner-report.md): обычно 450-800, максимум 1000 символов, 5-7 строк: тема → польза для читателя → 2-4 покрытых запроса → сила темы с конкретным основанием (или «спрос пока не подтверждён») → прямая ссылка. Никаких баллов проверки, путей, команд, названий агентов, таблиц. Одно сообщение, не поток. Если первая тема не прошла и взята запасная - одна фраза о причине. Провал - причина и нужное от владельца действие, без трассировок и обещаний.

## Критерий готовности этапа

- На площадке именно принятая версия; `work/published.json` содержит slug и id/url; повтор не создал второй записи.
- `work/<slug>/delivery.md` фиксирует сверку живой страницы: текст целиком на месте, ссылки, индексация.
- «Отправлено успешно» не равно «опубликовано успешно»; код 200 - не вся проверка.
- Одно уведомление владельцу отправлено.

## Ошибка и повтор

- Доставка не запускает новое написание принятого текста.
- Опубликованную статью не удалять ради «исправления» и не публиковать поверх заново без разрешения. Дефект уже опубликованной страницы → уведомить владельца со ссылкой, не называть статью черновиком и не делать её повтор.
- Смена slug после конфликта требует нового brief, нового claims.json по пути и новой приёмки; счётчик попыток не обнуляется.
- После публикации ошибки сообщать, не скрывать; чинить опубликованное - только с разрешения владельца.
