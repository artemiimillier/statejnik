# Ежедневный отбор тем

Дополнение к редакционному стандарту v3. В вопросе выбора темы этот файл заменяет старый подход «одна статическая очередь на месяц» и обязательные квоты кандидатов. Не меняет фактчек, финальную приёмку и правила публикации из основной методологии.

Режим применения: **каждый запуск по расписанию** (а также любой старт без явно заданной темы). Большой разведывательный заход на 20+ кандидатов из Этапа 1 основной методологии остаётся для первого запуска в новой нише или периодической пересборки портфеля - но он не отменяет ежедневную свежую проверку.

## Баланс слотов и недели

Если статейник работает по расписанию несколько раз в день, держите мягкий баланс направлений, например: поисковый вопрос / самостоятельный разбор свежего внешнего материала / полезное свежее изменение продукта ниши. Это не квота и не обязательный порядок. Нет достойного инфоповода - заменить сильной поисковой темой; важный релиз может вытеснить любой план. Не публиковать слабое ради доли источника.

На неделю фиксируются направления, не неизменяемые заголовки. Каждое утро новый пул; перед каждым следующим слотом - повторная проверка. При выборе читать свои отчёты за последние семь дней: не зациклились ли на одном продукте или источнике, не повторяете ли интент. При сравнимом качестве предпочесть недопредставленное направление. Отсутствие истории честно отметить; не выдумывать распределение и не считать запланированные/отклонённые статьи опубликованными.

## Минимальный рабочий цикл

1. **Снять снимок дня.** Один неизменяемый файл-снимок на дату (`work/topics/YYYY-MM-DD/snapshot.json`): наблюдаемый спрос (что доступно), окно данных, URL, время получения, статусы; реестр опубликованного и черновиков из `work/site.json` (site.py scan) и `work/published.json`. Повторный запуск возвращает тот же снимок и не выдаёт его за новый замер.
2. **Собрать новый пул** - каждый день, даже при полной очереди месяца. Источники параллельно: собственные поисковые наблюдения (подсказки поисковиков по 5-10 предметным запросам, доступные кабинеты вебмастера); официальные релизы и документация ниши; свежие внешние разборы и видео; вопросы аудитории при доступе. Статическая очередь и бэклог - только дополнительные идеи без обязательного приоритета. Сохранить сырые источники рядом со снимком. Нет доступа к каналу после фактической попытки - статус `unavailable`, не «вопросов нет». Не выгружать персональные данные.
3. **Свести 1-5 действительно разных кандидатов** в `work/topics/YYYY-MM-DD/research.json` (обычно 3-5, меньше при слабых доказательствах). Один winner, причина выбора и причина отложения остальных. Не заполнять строки ради квоты. Форма записи - ниже.
4. **Перед каждым слотом** заново открыть важные источники победителя, проверить версии/условия и прочитать соседние статьи по смыслу. Обновить `freshnessReview` и `intentReview` реальным временем проверки. Нулевой строковый матч не доказывает отсутствие каннибализации: семантическое суждение остаётся за агентом.
5. **Зарезервировать слот** (claim): повторить проверку под локальным замком и только при успехе создать `slot-N.json`. После этого можно писать, но это **не разрешение публиковать**. Слоты одного дня должны решать разные самостоятельные задачи, не разрезать одну инструкцию и не менять только бренд в H1. Заблокированный кандидат → другой интент либо честный пропуск слота, не рерайт занятого URL. При нескольких машинах локальный замок не распределённый: один writer, общая файловая система.
6. **После реальной публикации** закрыть резерв (`done` + фактический slug), предварительно GET-проверкой подтвердив публикацию. При неудаче - `release` с причиной: резерв архивируется, слот свободен для нового выбора. Черновики после release всё ещё блокируют дубли; их не удалять ради обхода. Самопроизвольного TTL нет: часы написания не должны освобождать чужую тему. После аварии проверить владельца замка; только убедившись, что процесс остановлен, убрать stale lock.
7. **Слот не заканчивается без публикации без попытки следующей темы.** При первом провале (модерация, фактология, технический отказ) не заканчивать на «не получилось»: повторить шаги 2-6 со следующим кандидатом из того же пула или свежим запасным (freshness + intent повторить, не брать из чужого резерва). Максимум **две попытки на слот** (две разные темы, не один и тот же материал дважды). Если обе не опубликованы - честно сообщить причину блокера и нужное действие, слот пометить как пропущенный. В отчёте владельцу (см. `references/owner-report.md`) всегда указывать, какая из попыток провалилась и почему.

## Что считать доказательствами

- **Собственный поисковый срез** (кабинет вебмастера, логи поиска по сайту) - наблюдения запросов **вашего сайта**, не рыночная частотность. Сохранять окно данных, объём выборки и лимиты выгрузки. Нет запроса ≠ 0 спроса. «Дыра» значит только отсутствие совпадения по текущему списку, не доказанный спрос.
- **Поисковые подсказки (suggest)** - реальные формулировки людей, косвенное свидетельство спроса. Пример: 10-15 базовых запросов ниши прогнать через подсказки основного поисковика вашего региона и записать варианты.
- **Официальный релиз**: точный URL, дата публикации, дата открытия, stable/prerelease, что изменилось и какую задачу читателя это затрагивает. Номер версии проверять по источнику, не угадывать. Не превращать каждый релиз в статью. Старое улучшение со свежей датой загрузки - не новое.
- **Внешнее видео/разбор**: URL, точная дата из метаданных (относительная дата выдачи предварительная), язык, заголовок, время наблюдения, реально полученные просмотры или null. Просмотры ролика на другом языке **не доказательство** спроса в вашем регионе. Скорость роста - только по двум сопоставимым замерам; нельзя делить просмотры на возраст и называть текущим ростом.
- **SERP**: запрос, дата, регион если известен, реальные URL и типы ответов; blocked/CAPTCHA - честно. **Вопрос аудитории**: анонимный кластер, число наблюдений и окно при реальном доступе; отсутствие доступа - не отрицательное свидетельство.
- **Область тем** - из `statejnik.yaml` (`research.watchlist`). Не новости ради хайпа, не обещания заработка, окупаемости, «без риска».

Каждый winner имеет `demandAssessment: {level: measured|proxy|unknown, evidenceIds: [], reason: "..."}`:

- `measured` - только реальные поисковые наблюдения с показами;
- `proxy` - SERP/suggest/вопросы аудитории (косвенное свидетельство, не частотность);
- `unknown` - проверено доступное, спрос не подтверждён (это не ноль). При `unknown` запрещён высокий confidence; в отчёте явно виден дефицит поисковых доказательств.

`confidence: low|medium|high` - качество доказательств с объяснением. `priorityScore: 0..10` - редакционный порядок на сегодня по полезности, свежести, доказательствам и отличию интента; **не вероятность трафика** и не гарантия позиций. Нет обязательного числового cutoff. Неподтверждённое существенное обещание блокирует публикацию даже при высоком балле.

## Внешнее видео как источник и самостоятельность

Разведке shortlist достаточно метаданных и описания. **Победителю, основанному на чужом ролике/разборе**, нужна полная расшифровка для приватного исследования (через ваш сервис транскрипции - `research.youtube.transcript_provider` из `statejnik.yaml`). Ответы сохранять приватно с правами 0600. Проверить фактический язык, наличие всех сегментов, начало/конец против длительности, отсутствие явных дыр. Пустой список дорожек в метаданных сам по себе не доказывает отсутствие транскрипции. Не называть summary полной расшифровкой. Частичная/заблокированная выгрузка → отложить этого winner или выбрать независимо подтверждённый сюжет.

Агент читает расшифровку целиком, делает карту ключевых идей, **условий и советов** с таймкодами; каждый значимый факт проверяет первоисточником. Карта - не только заголовки и крючки. Сохранить источники фактчека, точные ограничения, независимое оглавление и собственную добавленную ценность (проверка, пример, сравнение условий, воспроизводимый тест). Наличие файла расшифровки не доказывает полноту понимания и истинность утверждений.

**Не публиковать перевод или парафраз всего чужого материала.** Даже ссылка не разрешает заменять ролик полной текстовой копией. Два режима:

- `attribution: link-source` - используются уникальные кейсы/цитаты/эксперименты автора: явная ссылка и атрибуция, умеренные необходимые цитаты, без заимствования структуры. Ссылка должна реально попасть в источники итоговой статьи.
- `attribution: omit-source` - статья без ссылки: исключить уникальные кейсы/цитаты/эксперименты и последовательность чужого рассказа; использовать только самостоятельно подтверждённые факты и свой разбор. Исключение чужого уникального материала проверяет содержательная приёмка, не один boolean.

Полная расшифровка остаётся приватной: не идёт в текст статьи, git или публичные отчёты. Чужой денежный кликбейт из заголовка не переносить. Русский заголовок должен точно соответствовать самостоятельной статье.

## Форма research.json

Это схема-пример, **не реальные доказательства**: даты, URL и причины заменить результатами сегодняшнего исследования. `signals` допускают search/official/video/audience/serp; status ok/blocked/unavailable/empty. У неизвестной даты `publishedAt: null, ageDays: null`. Не выдавать blocked-сигнал за evidence победителя.

```json
{
  "date": "YYYY-MM-DD",
  "researchedAt": "ISO_TIMESTAMP",
  "channels": {
    "official": {"status": "ok", "reason": "Открыты URL релизов, записи в signals"},
    "video": {"status": "blocked", "reason": "Конкретная ошибка и URL попытки"},
    "audience": {"status": "unavailable", "reason": "Нет разрешённого доступа"}
  },
  "signals": [{"id": "release-1", "kind": "official", "status": "ok", "sourceUrl": "https://OFFICIAL/RELEASE", "observedAt": "ISO_TIMESTAMP", "publishedAt": null, "ageDays": null}],
  "shortlist": [{
    "id": "topic-1", "title": "Продукт X: какой канал обновлений выбрать", "targetKeyword": "продукт X stable обновление", "intent": "produkt-x:choose-update-channel",
    "confidence": "medium", "priorityScore": 7, "scoreMeaning": "editorial-priority-not-traffic-probability",
    "demandAssessment": {"level": "unknown", "evidenceIds": [], "reason": "Проверен собственный срез, подтверждённого запроса нет; не означает нулевую рыночную частотность"},
    "reason": "Почему сегодня; что подтверждено и чего не знаем", "addedValue": "Свой разбор выбора и условий отката, не перевод changelog", "evidenceIds": ["release-1"],
    "versionCheck": {"status": "verified", "sourceUrl": "https://OFFICIAL/RELEASE", "reason": "Проверено точное имя версии и канал"},
    "intentReview": {"reviewedAt": "ISO_TIMESTAMP", "comparedSlugs": ["реальный-соседний-slug"], "reason": "Чем задача отличается от ближайших published/draft/reservations"},
    "freshnessReview": {"reviewedAt": "ISO_TIMESTAMP", "evidenceIds": ["release-1"], "reason": "Заново открыты источники перед этим слотом, существенные условия актуальны"}
  }],
  "winnerId": "topic-1"
}
```

Для winner на основе видео добавить `videoResearch`:

```json
{"transcript": {"provider": "<ваш сервис>", "status": "complete", "path": "work/private-research/YYYY-MM-DD/ID-transcript.json", "language": "en"}, "ideaMap": [{"atSeconds": 42, "idea": "Проверенная идея", "conditions": "Когда действует", "advice": "Практический совет", "primarySourceUrl": "https://OFFICIAL/DOC", "factCheck": "verified"}], "independentOutline": ["Наша задача", "Наш проверяемый подход"], "addedValue": "Что именно проверяем сами", "attribution": "omit-source", "excludedUniqueMaterial": true}
```
