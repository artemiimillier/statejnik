# Чек-лист SEO + GEO (Generative Engine Optimization)

> **Когда читать:** перед публикацией статьи под поисковый трафик. Канонический источник всех проверок Этапа 13 (SEO/GEO-аудит на проде). Конкретные пороги и пути держите тут, чтобы менять без правки методологии.
>
> **Зачем:** одновременно оптимизировать под классический поиск (Google, Bing, Яндекс и др.) и под цитирование языковыми моделями (Perplexity, ChatGPT browse, Claude web search, Gemini, нейро-выдачи). Это две дисциплины, но ~80% работы пересекается.
>
> **Приоритет редакционного стандарта v3.** Для новых статей правила смысла, языка, структуры, SEO и приёмки из `references/editorial/editorial-standard.md` старше конфликтующих пунктов ниже. Старые квоты объёма, синтаксиса и показатели «машинности» не являются критерием качества; технические блокировки площадки не обходить. Финальную языковую вычитку проводить до публикации.
>
> **Главный принцип:** этот файл - единая точка истины для SEO+GEO проверок. Агент перед публикацией пробегается по разделам 1-9 сверху вниз. Каждый раздел = один или несколько проверяемых пунктов. Что отдаёт ваша CMS (микроразметку, карту сайта, реестры для языковых моделей) - инкапсулировано за адаптер площадки (publish.py); пути реестров - в `config.*`.

## 1. Машино-читаемые реестры сайта (база)

Перед добавлением чего-то нового - знать, что ваша CMS уже отдаёт. Это родовые механизмы, поддерживаемые любым движком:

| Артефакт | Что делает |
|---|---|
| `sitemap.xml` | Карта сайта с приоритетами по типу статьи (опорная = 1.0, инструкция = 0.8). Новая статья попадает автоматически, если CMS подтягивает все опубликованные. |
| `robots.txt` | Боты поисковиков и языковых моделей явно разрешены (краулеры основных поисковых систем + AI-ассистентов). Закрываем только то, что реально не нужно в датасеты. |
| Структурированная разметка (JSON-LD) | Граф `Article` + `Person` + `WebPage` + `BreadcrumbList` (+ `HowTo` для инструкций, `FAQPage` для блоков вопрос-ответ, `VideoObject` если есть видео). Генерит адаптер площадки (publish.py). |
| Реестр для языковых моделей (если CMS отдаёт) | Текстовый индекс/дамп статей по стандарту `llmstxt.org`. Путь - в `config.*`. См. раздел 8: это вспомогательный, не основной сигнал. |
| Markdown-версия страниц (если CMS отдаёт) | Чистый Markdown без HTML-обёртки для краулеров языковых моделей. Главная работающая GEO-практика - см. раздел 8. |

**Что критично использовать как есть:** реестры собираются из данных CMS - новая статья попадает туда сама. Не пересоздавать руками.

## 2. GEO-паттерны цитируемости (9 правил) - для языковых моделей

Это правила структуры, по которым ИИ-ассистент **выдёргивает пассаж как цитату**. Ни один формат не гарантирует попадания в ответы поисковиков или ИИ: проверяем полезность и точность, а результат измеряем отдельно.

⚠️ **Поправка редакционного стандарта v3:** это рабочие эвристики, а не доказанная гарантия цитирования. Не портить живой русский текст ради формальных квот: «50% H2 в форме вопроса» - ориентир, а не требование; если вопрос в H2 звучит натянуто, пиши утвердительный заголовок-ответ. При конфликте между GEO-квотой и понятностью для человека побеждает человек.

### 2.1. Answer-First параграф 40-75 слов в начале каждого H2

Первый параграф каждого раздела должен **сразу отвечать на вопрос H2**, без трёх параграфов подводки. Короткий точный ответ, как в энциклопедии.

**Правило v3:** короткий прямой ответ нужной длины, с существенными условиями. 40-75 слов - ориентир, а не диапазон, который надо добирать словами.

**Что проверять:** ответ понятен и не повторяется следующим абзацем. Если блок-резюме требует шаблон площадки или `structure-check.py` - соблюдать, но не считать это SEO-гарантией.

### 2.2. Question-Based заголовки H2

«Как настроить X?», «Зачем нужен Y?», «Что такое Z?» - а не «Настройка X», «Y», «Определение Z». До 10 слов.

**Что проверять:** каждый H2 - вопрос или утвердительный ответ на вопрос. Доля вопросов не нормируется: заголовок должен помогать найти ответ.

### 2.3. Standalone-секции

Каждый H2 + его контент должен работать **без чтения соседних секций**. Модель цитирует кусок вне контекста соседей.

```bash
grep -niE '(как мы видели выше|выше упомянут|ниже мы рассмотрим|продолжая тему|в продолжение)' <path>
```

Каждое попадание - переписать на standalone-формулировку.

### 2.4. Параграф = 2-4 предложения, одна идея

Длинные параграфы модель режет посредине → искажает смысл. Короткие - целиком цитируются.

**Что проверять:** абзац понятен и раскрывает одну связную мысль. Делить по смыслу, не по числовой квоте.

### 2.5. Сравнения = таблицы, не сплошной текст

Симметричные критерии удобно сопоставлять в таблице `| Признак | A | B |`. Отраслевые «множители цитирования» для таблиц не подтверждены для ваших материалов - не использовать их как основание.

**Что проверять:** таблица помогает сопоставить одинаковые критерии. Квоты таблиц нет; причинные объяснения можно оставить связным текстом.

### 2.6. Процессы = нумерованные списки

«Сделай X, потом Y, потом Z» - **нумерованный** список (`1. 2. 3.`), не маркеры (`- - -`). Нумерация передаёт порядок действий; обещания множителя цитирования не используем. Маркеры - только для неупорядоченных перечислений (характеристики, признаки).

### 2.7. Fact-dense предложения с именованными источниками

«По данным [X](url)…», «<Источник> сообщает что…» - конкретные числа, даты, имена источников. Не «по слухам», «как многие говорят», «вроде бы». Каждая цифра имеет ссылку или её проверил факт-чекер. Цитаты - с атрибуцией (автор + источник).

### 2.8. Явное именование сущностей

«<Сущность> сделала X», а не «оно сделало X». Повторять название нужно, если иначе неясно, к какому объекту относится действие.

**Что проверять:** у местоимения понятный референт. Не повторять бренд механически через фиксированное число предложений.

### 2.9. Чистый семантический HTML

Настоящие `<h1>`, `<h2>`, `<ol>`, `<table>` - не styled `<div>`. Если ваш движок рендерит структуру через семантические теги - убедиться, что парсер не подменяет их на оформительские.

## 3. Schema.org JSON-LD (best practices)

> Если адаптер площадки (publish.py) микроразметку не генерит - закрыть весь раздел как `[x] SKIP: CMS не генерит schema`.

### 3.1. Какие типы держать

| Тип | Где |
|---|---|
| `Article` | основной |
| `Person` (автор + ревьюер, если есть) | author / reviewedBy |
| `WebPage` + `mainEntityOfPage` | mainEntityOfPage |
| `HowTo` + `HowToStep` | для инструкций |
| `FAQPage` + `Question` + `Answer` | для блоков вопрос-ответ |
| `VideoObject` | если есть видео |
| `BreadcrumbList` | навигация |
| `Organization` | издатель (publisher) |

⚠️ **Лицензируемые типы под запретом.** Если в вашей нише есть форматы, которые по закону вправе использовать только обладатель лицензии/сертификата - соответствующие типы разметки тоже под запретом (держите их в `editorial.banned_words`, проверка - в `references/checklists/compliance.md`). Должны остаться только нейтральные типы.

### 3.2. E-E-A-T через `Person` - что обязательно

Главный сигнал авторитета. У `Person`-объекта:

```json
{
  "@type": "Person",
  "name": "<имя автора, без должностей в строке>",
  "url": "<страница автора>",
  "jobTitle": "<должность отдельным полем>",
  "knowsAbout": ["<тема экспертизы 1>", "<тема 2>", "<тема 3>"],
  "sameAs": ["<публичный профиль 1>", "<профиль 2>", "<профиль 3>"]
}
```

**Что проверять:**
- `Person.name` - только имя (без должностей и префиксов вроде «Dr.», «Senior Engineer»).
- `jobTitle` - отдельным полем.
- `knowsAbout` - массив тегов экспертизы (тематическая авторитетность).
- `sameAs` - массив URL на публичные аккаунты автора (соцсети, видеоплощадки, профили). **Минимум 3.** Это главный E-E-A-T сигнал.
- `sameAs` ведёт на страницу, которая идентифицирует **того же человека**: профиль, а не инвайт в группу или чат (ссылки вида `t.me/+…`, `…/join/…` не считаются). Реальный случай: из четырёх ссылок две оказались инвайтами, валидных осталось две при требовании 3+. То же для `Organization.sameAs`.
- `knowsAbout` - устойчивый набор экспертизы автора, а не рубрики конкретной статьи. Реальный случай: шаблон заполнял поле тегами каждого материала, и у автора на каждой странице была «другая» экспертиза - сигнал размывался по всему сайту.

### 3.3. Что требуют поисковики

- `author.name` - только имя, без префиксов.
- Несколько авторов - каждый отдельным элементом массива, не строкой через запятую.
- ISO 8601 для дат **с timezone**: `2026-05-18T10:00:00+03:00`.
- `dateModified` обновлять при **каждой правке** - сигнал свежести.

### 3.4. FAQPage - rich results свернулись, но ИИ цитирует

Часть поисковиков убрала FAQ rich results, но AI Overviews, по отраслевым замерам, цитируют страницы с `FAQPage` schema чаще (замер не проверен на вашем сайте). **Оставляем как есть.** Не оставлять `FAQPage` без `dateModified` - модель парсит даже без rich-result. Разметка обязана соответствовать видимому содержимому: не добавлять FAQ/HowTo/рейтинги ради обещания расширенного сниппета, и не выдавать наличие JSON-LD за рост позиций (стандарт v3).

### 3.5. Валидация

```bash
# Compile-time типизация (если стек на TypeScript): подключить пакет типов Schema.org.
# Runtime-валидация перед публикацией - публичным валидатором структурированных данных:
#   прогнать URL статьи через валидатор Schema.org и Rich Results Test.
```

Проверять: все типы валидны, нет warning'ов про обязательные поля (`datePublished`, `dateModified`, `headline`, `image`).

### 3.6. Разметка против видимого текста - типовые дефекты

- **FAQ без schema.** Раздел вопросов, написанный обычным текстом (`**Вопрос?** ответ`), не даёт `FAQPage`, если генератор разметки ищет только специальный блок вопросов вашей CMS. Это дефект материала, а не платформы: проверять на каждой статье с FAQ-разделом.
- **Ответы FAQ не в HTML.** Аккордеон рендерится на сервере только кнопками, ответ появляется в DOM по клику. Разметка собирается, но текстовые краулеры видят вопросы без ответов. Реальный случай: из семи ответов в читаемом HTML ноль, на втором материале подряд - то же, то есть дефект системный. Проверять `curl` исходного HTML: ответы должны быть в тексте страницы, а не только в `<script>`.
- **Дубль заголовка FAQ.** Свой `## Частые вопросы` плюс блок FAQ с заголовком по умолчанию дают два одинаковых заголовка подряд. Оставить один.
- **`HowTo` склеивает разные процедуры.** Два блока шагов в статье («как проверить» из 5 шагов и «что делать, если…» из 6) собрались в один `HowTo` из 11 шагов с названием статьи - инструкции, которой не существует. Нужен один `HowTo` на процедуру или отказ от схемы при двух и более блоках.
- **Дубль в `BreadcrumbList`.** Два уровня крошек ведут на один URL - кривая крошка в выдаче.

## 4. Сигналы свежести и evergreen-контента

### 4.1. Год в title/H1 - только если год меняет ответ

Конструкция «<тема> в <текущий год>» работает на цитируемость, **только когда актуальность действительно меняет ответ** (тарифы, версии, доступность). Стандарт v3: не вписывать год механически в каждую evergreen-статью и не обновлять дату без реальной проверки содержимого - поисковик умеет отличать свежесть от косметики.

### 4.2. `dateModified` обновлять при правках

При каждом редактировании - обновлять дату модификации статьи (многие CMS делают автоматически). Попадает в `dateModified` JSON-LD.

### 4.3. Регулярный пересмотр опорных статей

Evergreen-статьи (опорные, инструкции с year-suffix) пересматривать **раз в 60-90 дней**. Минимум - обновить дату последнего обзора, добавить пункт в журнал изменений внутри статьи. Если у вашей CMS есть автонапоминание об устаревании (>90 дней без обновления) - использовать его.

## 5. Уведомление поисковиков об индексации

### 5.1. Мгновенный пинг (главный канал для части поисковиков)

- Механизм мгновенного оповещения об индексации - индустриальный, поддерживается основными поисковыми системами (кроме одной крупной - она индексирует обычным обходом).
- Submit делает адаптер площадки (publish.py) после публикации, либо вы вручную через кабинет вебмастера.
- Проверить, что пинг ушёл в **несколько** поддерживающих систем, а не в одну (`python3 $SKILL_DIR/scripts/publish.py ping <url>`; ключ - `INDEXNOW_KEY` в `.env`).
- Результат пинга должен быть виден: код ответа (200/202) в выводе или логе. Реальный случай: функция пинга при отсутствии ключа молча возвращала «пропущено», вызов шёл без обработки результата - отправку нельзя было подтвердить, а одна из систем не вызывалась вовсе. Отсутствие ключа в локальном `.env` ничего не говорит о рабочем сервере - проверять там, где реально идёт отправка.
- Если механизм требует публичный файл-ключ - убедиться, что он доступен по объявленному адресу.

### 5.2. Кабинеты вебмастеров

Submit карты сайта - автоматически. Раз в неделю можно тянуть топ-запросы через API кабинета для аналитики «по каким фразам нашли статью».

### 5.3. Поисковик без мгновенного пинга

Submit карты сайта (делается один раз). Индексация - обычным обходом (часы-сутки). Проверить, что статья появилась в `sitemap.xml` (она подтянется автоматически из опубликованных) и что сброшен кэш страницы (on-demand revalidation / очистка CDN по пути).

## 6. Core Web Vitals и Performance

### 6.1. Бюджеты (на p75 реальных пользователей, mobile)

| Метрика | Цель | Что значит |
|---|---|---|
| **LCP** | < 2.5s | Largest Contentful Paint - самый большой видимый элемент |
| **INP** | < 200ms | Interaction to Next Paint - отзывчивость на действие |
| **CLS** | < 0.1 | Cumulative Layout Shift - насколько прыгает вёрстка |

Значимая доля сайтов проваливает именно INP - самая частая проблема (длинные JavaScript-задачи на клиенте).

### 6.2. Lab-бюджеты (в pre-deploy через любой Lighthouse-совместимый прогон)

| Метрика | Цель |
|---|---|
| Performance score | ≥ 90 |
| Accessibility | ≥ 95 |
| SEO | = 100 |
| Best Practices | ≥ 90 |
| FCP | < 1.8s |
| TBT | < 200ms (proxy для INP) |

### 6.3. Как измерять

- **CI-вариант:** прогон Lighthouse в pre-deploy с budget-файлом, блокировать merge при провале бюджета.
- **Быстрый вариант:** ручной прогон публичного измерителя скорости (PageSpeed Insights и аналоги - индустриальный стандарт) для mobile и desktop отдельно.
- **Честность замера.** Анонимная квота API PageSpeed быстро упирается в HTTP 429, веб-интерфейс через извлечение страницы отдаёт пустую оболочку. Локальный Lighthouse - это лаборатория, не поле: полевые CWV на p75 им не подтверждаются. Пока нет ключа API или полевых данных, пункт «Performance ≥ 90» записывать как **непроверенный**, а не как пройденный.

Типовые причины провала:
- LCP - тяжёлая обложка без оптимизации, нет lazy-load у картинок ниже первого экрана, шрифты блокируют рендер.
- INP - длинные JS-задачи на клиенте.
- CLS - картинки без заданных width/height, динамические баннеры, которые «прыгают».

### 6.4. Типовые дефекты шаблона статьи (реальные случаи)

Это дефекты платформы, а не одной статьи: найдено на одной - проверить на всех и сообщить владельцу отдельным инфраструктурным пунктом, не чинить платформу самовольно.

- **`preload` греет не тот файл.** `<link rel="preload" as="image">` указывает на `hero.webp`, а `<picture>` отдаёт браузеру `hero.avif`: браузер качает оба, предзагрузка не помогает. В реальном случае задержка загрузки составила 40% LCP, mobile LCP 5,7 с при цели 2,5 с. «Preload стоит» ≠ «preload работает»: сверять формат в `preload` с тем, что реально выбирает `<picture>`.
- **Формат картинки.** Утверждение «AVIF тяжелее WebP и качается зря» на одном материале подтвердилось, на следующем - нет (AVIF легче на 1,7 КБ). Проверять размеры на каждом замере, а не считать данностью.
- **Нет `srcset` у обложки** - одна ширина на все экраны, лишний трафик и мобильный LCP.
- **`Cache-Control: private, no-store` на публичных страницах** - ни CDN, ни браузер не кешируют, каждый визит идёт до сервера. Обычно побочный эффект middleware, ставящего куки на каждый ответ. Бьёт по TTFB, LCP и повторным визитам. Проверка: `curl -sI <url> | grep -i cache-control` для обычного UA и бота.
- **Два `og:image`** с разными размерами на одной странице - непредсказуемое превью при шеринге.
- **Доступность:** якорные ссылки заголовков без доступного имени (`link-name`), перескок уровней `h2 → h4` в блоке шагов (`heading-order`), недостаточный контраст - A11y застревает на 91-94 при цели 95.
- **Ошибки гидратации** на клиенте - Best Practices 74-75 и риск расхождения серверного и клиентского HTML.

## 7. Open-source инструменты (опционально)

## 8. Markdown-альтернатива страниц (главный GEO-gap)

Лидеры рынка отдают `.md`-версию каждой страницы для краулеров языковых моделей. Это **самая работающая GEO-практика** - важнее самого реестра для языковых моделей.

### 8.1. Как работает

Краулер запрашивает страницу с `Accept: text/markdown` ИЛИ суффиксом `.md`. Сервер отдаёт **чистый Markdown без HTML-обёртки**, навигации, виджетов, футеров. Модель получает контент без шума.

### 8.2. Проверка

```bash
# Если CMS умеет отдавать markdown-версию - она работает:
curl -s -H "Accept: text/markdown" https://<config.project.domain><config.project.content_path>/<slug>
# Ожидаем чистый markdown, не HTML.
```

Реализация - за адаптер площадки (publish.py) (route-handler с детектом `Accept`/UA краулеров + редирект `/<slug>.md`). Реестр для языковых моделей (раздел 1) - вспомогательный сигнал, перегретый по реальному эффекту: делать минимально, не вкладываться как в основной. Markdown-экспорт важнее.

## 9. Полный pre-publish gate (SEO+GEO)

Перед публикацией на прод - все пункты:

### Контент (GEO-структура)
- [ ] H1 содержит `target_keyword` (+ текущий год, только если год меняет ответ)
- [ ] Заголовки H2 понятны без тела; вопросная форма - где естественна, без квоты
- [ ] В начале каждого H2 короткий прямой ответ с условиями (40-75 слов - ориентир, не квота)
- [ ] Абзац - одна связная мысль (2-4 предложения - ориентир)
- [ ] Standalone-секции (без «как мы видели выше»)
- [ ] Сравнения по симметричным критериям - таблицей (квоты таблиц нет)
- [ ] Процессы - **нумерованные** списки
- [ ] Все цифры со ссылкой на источник
- [ ] Явное именование сущностей: у местоимений понятный референт
- [ ] FAQ-раздел оформлен блоком, который даёт `FAQPage`; ответы видны в исходном HTML; заголовок FAQ не задвоен

### Schema.org / E-E-A-T (или SKIP, если CMS не генерит)
- [ ] JSON-LD валидируется (публичный валидатор / Rich Results Test)
- [ ] `Article` + `Person` + `Organization` + `BreadcrumbList` присутствуют
- [ ] `Person.knowsAbout` заполнен
- [ ] `Person.sameAs` включает 3+ публичных профиля автора (профили, не инвайты)
- [ ] `HowTo` - по одному на процедуру, без склейки разных блоков шагов
- [ ] Нет лицензируемых/запрещённых типов из `editorial.banned_words`

### Технический SEO
- [ ] Lighthouse mobile: Performance ≥ 90, SEO = 100, A11y ≥ 95 (не удалось замерить - «не проверено», не «пройдено»)
- [ ] LCP < 2.5s, INP < 200ms, CLS < 0.1 на p75 (лабораторный замер не заменяет полевой)
- [ ] `meta_title` ≤ 70 символов
- [ ] `meta_description` 100-160 символов - **посчитано командой, не на глаз**: `python3 -c "import sys;print(len(sys.argv[1]))" "<текст description>"`. Реальный случай: description «примерно 155» оказался 173 символа и был пойман только аудитом после публикации.
- [ ] OG-image сгенерирован и работает (если `config.image.tool` задан)
- [ ] Canonical URL установлен

### Индексация
- [ ] Статья в `sitemap.xml` (curl-тест: `grep <slug>`)
- [ ] Статья в реестре для языковых моделей, если CMS его отдаёт (curl-тест)
- [ ] Markdown-версия отдаётся, если CMS умеет (curl с `Accept: text/markdown`)
- [ ] Пинг индексации ушёл в несколько поддерживающих поисковиков, код ответа записан
- [ ] Кэш страницы сброшен (revalidate по пути)

### GEO-проверка ботом
- [ ] Контент виден прямо в HTML (не подгружается JS) - проверить `curl -A "<UA-бота>"`
- [ ] Структурированная разметка читается (`application/ld+json` в HTML)
- [ ] Нет `noindex` / `nofollow`
- [ ] HTTP 200 для бота, а не 403 (защита от ботов не рубит полезных краулеров)
- [ ] Нет клоакинга: разные User-Agent (обычный браузер, Googlebot, YandexBot, краулеры ИИ) получают одинаковый HTML
- [ ] `Cache-Control` публичной страницы не `private, no-store`

### Свежесть и кластер
- [ ] `dateModified` обновлён
- [ ] Статья привязана к 1-3 рубрикам (Этап 9a)
- [ ] Внутренние ссылки на 3+ реально опубликованные статьи вашего `content_path` (`work/site.json`, `work/published.json`; порог - `tools.structure.min_internal_links`), без ссылок на будущие статьи и без набивки ради квоты
- [ ] Если есть опорная статья - установлен `parent_slug`

## 10. Что НЕ делать (контр-практики)

- Не вкладываться в реестр для языковых моделей как в основной сигнал - он сейчас декоративный (мизер хитов на фоне общего AI-bot-трафика). Делать минимально.
- Не оставлять `FAQPage` schema без `dateModified` - ИИ парсит даже когда rich-result свёрнут.
- Не отдавать краулерам языковых моделей HTML с навигацией/футером/виджетами - это шум.
- Не разрешать краулеры-скрейперы, которые не дают реферального трафика, если контент не нужен в их датасеты.
- Не публиковать ежедневно низкокачественные статьи - алгоритмы полезного контента наказывают за churn.
- Не использовать сплошной текст для сравнений - оформлять таблицей.
- Не разбивать одну идею на 7 параграфов - собрать в один 2-4 предложения или в таблицу.
- Не вписывать год в H1 механически и не обновлять дату без проверки содержимого.
- Не добавлять FAQ, HowTo или рейтинги ради обещания расширенного сниппета - разметка отражает только видимое содержимое.
- Не считать чек-лист пройденным по наличию файла или тега: «preload стоит», «ключ есть», «schema собралась» проверять по фактическому поведению страницы.
